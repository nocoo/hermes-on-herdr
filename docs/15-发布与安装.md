# 15 · 发布、安装与版本管理

本指南对应 **0.1.2**，正式分发记录见 [GitHub Release](https://github.com/nocoo/hermes-on-herdr/releases/tag/v0.1.2)。它是早期 0.x 版本，使用已有命名 Profile 和手动配置；一键关联向导是[下一步设计](16-首次安装与Profile关联.md)，尚未实现。Release 页面记录的实际 tag、commit 和验证结果是发布依据。

## 分发方式

使用 GitHub 仓库、不可变的 Git tag 和 Herdr 原生插件安装器。分发内容就是源码、manifest、launcher 和固定的 hqtui 源码；运行时复用用户已有的 Hermes Python 环境。安装或启动插件不会下载依赖。

用户在目标 Herdr session 的终端执行：

```sh
herdr plugin install nocoo/hermes-on-herdr --ref v0.1.2
```

Herdr 会展示插件名称、版本、解析后的 commit、hooks 和 actions，再确认安装。安装器默认启用插件，但没有配置和运行意图时不会启动 Gateway；缺少配置的 hook 会返回 `SETUP_REQUIRED`，不会进入关联向导。`--yes` 供已经审阅过来源的非交互安装使用。安装始终指定 tag，避免用户无意间跟随 `main` 更新。`--session NAME` 可明确指定宿主 session。

这条命令及行为依据 Herdr **0.9.0** 的 `src/cli/plugin.rs::plugin_install`、`git_checkout` 和 `register_installed_plugin` 核对。它按 Git ref 获取源码，不依赖 Release 附件；[源码基线](09-源码证据索引.md)固定在同一提交。

Release 附带从 tag 导出的 `hermes-on-herdr-0.1.2.tar.gz` 和 `SHA256SUMS`，包含 manifest、可执行 launcher、运行源码、文档和 vendored hqtui。它不是独立 Python 环境或系统服务安装包。下载后在附件所在目录执行 `shasum -a 256 -c SHA256SUMS`（macOS）或 `sha256sum -c SHA256SUMS`（Linux）。官方安装仍使用上面的 Herdr 命令；安装后核对列表中 `source.kind=github`、`requested_ref=v0.1.2` 和 `resolved_commit` 与 Release tag 一致。

## 运行条件

| 项目 | 0.1.2 要求 |
| --- | --- |
| 操作系统 | macOS 或 Linux，同一机器、同一普通用户 |
| Herdr | 0.9.0；运行时检查确切版本，manifest 的最低版本不代表任意新版本已兼容 |
| Hermes | v0.21.1，源码提交 `b7ac3ba1cdf89f94dfe86de27e01358b194f4053` |
| Python | Hermes venv 中的 Python 3.11+；系统 `/usr/bin/python3` 承担隔离启动引导和恢复中心，交互恢复需要 curses |
| 依赖 | [requirements.txt](../requirements.txt) 中的 psutil 和 PyYAML；hqtui 已随仓库提供 |
| Profile | 用户自行配置的已有命名 Profile；模型、凭据、消息平台已就绪，满足[专用配置要求](../examples/README.md) |
| 权限 | Profile 和插件配置目录 `0700`，私有配置文件 `0600`，路径不允许其他用户写入 |

Linux 使用相同的 launcher、Unix socket、文件锁和 PTY。进程身份由 `/proc` 的启动 ticks 与 boot ID 核验，需要能读取本用户进程信息。内核支持时使用 pidfd 发送信号；旧内核返回 `ENOSYS` 时，重新核验身份后退回常规信号，权限错误仍报告失败。

macOS 退出中的进程可能先失去 argv，再被内核标记为 zombie；插件在权限错误后最多短暂等待 20 ms 来核验真实退出，不调用 `waitpid` 抢先回收子进程，保证 0/75/78 的退出策略不丢失。仍存活且身份不可读时保持 UNKNOWN，不据此启动替代实例。

可执行文件及其解析后路径的父目录不能被其他用户写入。Homebrew 的组可写 bin/Cellar 常被拒绝；可把已核对版本和摘要的 Herdr 二进制复制到私有目录，不修改 Homebrew 的目录权限。Python 保留实际可用的私有 Hermes venv 路径，不能把 venv symlink 改写为底层解释器路径。CI 的共享 toolcache 使用 `venv --copies` 隔离，权限检查本身未放宽。

插件不安装 launchd 或 systemd 服务。已有系统服务与插件不能同时管理同一 Profile。常规 Ubuntu/Debian/Fedora 用户环境是兼容目标；非标准 `/usr/bin/python3` 布局、受限 `/proc`、容器内运行 Herdr，以及其他发行版仍需各自验证。路径通过 Herdr 查询或配置定位，不硬编码 macOS 的用户目录。

## 当前可用的手动接入

以下是**新安装**的过渡流程，已有安装使用后面的升级流程。

1. 用户先用 Hermes 配好命名 Profile，例如 `cherry`。插件沿用该名称，不创建、克隆或改名。若当前由原生服务管理，先阅读下方接管顺序；不能让两个管理器同时启动同一 Profile。
2. 安装后暂时禁用注册，查询实际配置及代码目录：

   ```sh
   herdr plugin disable nocoo.hermes-gateway
   herdr plugin config-dir nocoo.hermes-gateway
   herdr plugin list --plugin nocoo.hermes-gateway --json
   ```

   使用 `config-dir` 输出的目录和列表中的 `plugin_root`。不要手拼 Herdr 的内部路径，以支持不同系统和自定义 XDG 目录。

3. 按[配置示例](../examples/README.md)创建私有 `config.json` 和 `runtime-python`。`profile_id`/`profile_home` 指向所选 Profile；`owner_socket` 取目标 session 内的 `HERDR_SOCKET_PATH`；`agent_cwd` 与 Profile 的 terminal 工作目录一致。可执行文件使用实际绝对路径，Python 保留 venv 路径。缺少依赖时在该 venv 中安装 requirements；启动时不运行 pip。
4. 进入实际 `plugin_root`，把下面的占位路径换成配置路径，查看计划并初始化暂停的绑定：

   ```sh
   ./bin/hermes-on-herdr --version
   ./bin/hermes-on-herdr --config /absolute/config.json bind --dry-run
   ./bin/hermes-on-herdr --config /absolute/config.json bind --apply
   herdr plugin enable nocoo.hermes-gateway
   ./bin/hermes-on-herdr --config /absolute/config.json doctor --json
   ```

5. 在绑定的 Herdr session 内显式启动，再检查就绪：

   ```sh
   ./bin/hermes-on-herdr --config /absolute/config.json start
   ./bin/hermes-on-herdr --config /absolute/config.json status --require-ready
   ```

   hook 外的控制命令可使用全局 `--owner-socket /absolute/bound.sock`。`status --require-ready` 是单次检查，尚未 READY 时退出码为 10；由调用者在期限内重复检查。Start 的接受回执不等于 READY，还需在消息平台做一次真实往返。0.1.2 始终打开完整 Dashboard，不再询问是否开启；暂停 Gateway 后仍保留面板。

`bind` 只创建或校验私有绑定，不接管外部服务，也不保证此后一直没有竞争者；实际启动还会检查 Profile 占用、固定 inode 的锁和进程身份。重复绑定保留现有意图和熔断。Doctor 检查配置、固定源码版本和 owner，并读取状态；`real_validation=NOT_RUN` 表示这条诊断命令本身不执行消息端到端或宿主生命周期验收。

需要网页健康入口时，在独立 Herdr pane 中运行：

```sh
./bin/hermes-on-herdr --config /absolute/config.json dashboard --http-port 8767
curl --fail http://127.0.0.1:8767/health
```

网页地址为 `http://127.0.0.1:8767/`。这是已经实现、默认不自动启动的独立只读模式；终端监控继续可用。只在新鲜 READY、实际 Gateway/pane 归属及期望平台连接均满足时，健康接口返回 200；失败或采样过期返回 503。详细语义见[面板指南](14-hqtui监控面板.md#148-本机网页与健康检查)。

本地开发使用 `git clone` 和 `herdr plugin link /absolute/hermes-on-herdr --disabled`。Herdr 不允许 GitHub 安装直接覆盖本地 link：先完成插件停服、禁用和 `herdr plugin unlink nocoo.hermes-gateway`，再执行官方安装，并按查询结果更新私有配置中的 `plugin_root`。`unlink` 解除注册，保留配置与 Profile；不能通过修改 registry 把本地源码伪装成已安装的 Release。

## 恢复命令的安装

0.1.2 提供独立恢复入口。进入实际 `plugin_root` 后，为已在 PATH 中的 `~/.local/bin` 建立一次链接：

```sh
mkdir -p "$HOME/.local/bin"
ln -s "$PWD/bin/hermes-on-herdr" "$HOME/.local/bin/hermes-on-herdr"
hermes-on-herdr recover --snapshot
```

已有同名命令时先核对链接，复用正确入口，不覆盖其他程序。确认 shell 的 PATH 包含 `~/.local/bin`。此后用户只需执行 `hermes-on-herdr`；它按 `HERDR_PLUGIN_CONFIG_DIR` 或 Herdr 的默认 / XDG 配置目录寻找本插件的 `config.json`，不会扫描或选择别的 Profile。控制按钮从保存的配置取得 owner，当前 Herdr context 指向其他 session 时拒绝控制。

不使用 shell 入口时，也可在 Herdr 的命令面板选 **hermes on herdr: Recovery & Repair**。对应原生命令为：

```sh
herdr plugin action invoke recover --plugin nocoo.hermes-gateway
```

恢复中心使用 `/usr/bin/python3` 的标准库；交互终端需要 curses。不会在启动时自动安装依赖。用户点击“修复插件依赖”后，才在配置的 venv 中执行本插件 `requirements.txt`，并要求 pip 确认当前为虚拟环境。没有可用系统 Python 或插件文件已丢失时，需要先恢复安装。详细行为见 [故障恢复入口](14-hqtui监控面板.md#149-故障恢复入口)。

## 从原生服务或开发 link 接管

先检查真实 `HERMES_HOME`、Profile、启动时间、父子进程链、原生 identify/status、supervisor、lifetime lock 和 launchd/systemd 注册。保存该 Profile 的服务定义、私有配置与控制状态；备份不提交 Git。不同 Profile 可以并行运行，不能按进程名批量停服。

尽量在原生 Gateway 仍在线时准备源码、依赖和配置。插件的绑定必须保持 paused；从开发 link 更换来源时，按下方升级顺序停止 Gateway、禁用插件并关闭已核验归属的专用 pane，确认 Gateway、后代及 supervisor 已退出，再 unlink 和安装指定 tag。安装自动启用后仍保留 paused；更新 `plugin_root` 并通过 Doctor。只读独立面板需另行退出并从新 checkout 重开。

完成准备、确认已获停服授权后，停止**该 Profile**的原生管理器，防止 KeepAlive 再拉起；确认旧 wrapper/Gateway 确实退出、没有其他 owner 或持锁实例，再显式 Start。不要删除或替换 `gateway.lock` 来绕过占用检查。已在前一阶段移除的服务无需重复停用；保留其他 Profile 的原生服务。

验收需同时记录：唯一 Gateway 的 Profile、PID/start、PPID/SID；Herdr pane 的 shell PID 为 supervisor；已安装插件的路径/版本/来源；两次新鲜原生平台连接证据；插件 READY；网页健康 200；原生服务无重复实例。连接成功不等于模型或消息往返验证。

启动失败时，先核验插件及其 Gateway 已退出，再恢复备份中的原生管理器；进程归属不明时不能并行启动回滚实例。若准备阶段就发现阻碍安全切换的问题，保留原生在线服务并报告具体阻碍。

## 版本约定

| 位置 | 0.1.2 的值 | 用途 |
| --- | --- | --- |
| `src/hermes_gateway_herdr/__init__.py` | `0.1.2` | CLI、doctor、TUI 共用的运行时版本 |
| `herdr-plugin.toml` | `0.1.2` | Herdr 列表及安装预览 |
| Git tag | `v0.1.2` | 发布后固定到已验证的 commit |
| GitHub Release | `hermes on herdr 0.1.2` | 功能、安装、兼容性和限制说明 |

运行时读取常量，不启动 Git、不探测网络，也不在每帧解析 manifest。保留 manifest 字面版本供安装前读取，测试保证它与运行时一致，tag CI 再检查 tag 名。`--version` 无需配置，兼容旧 launcher 名称。完整面板右下角显示 `v0.1.2`，极窄视图也保留版本。

默认遵循 SemVer：`0.1.x` 用于修复、性能和兼容性改进；`0.2.0` 用于新增功能，0.x 中不兼容的配置、所有权或行为变更也必须提升 minor，并说明迁移。1.0 后不兼容变更提升 major。预览候选使用 `0.2.0-rc.1` / `v0.2.0-rc.1`。发布过的 tag 不移动、不覆盖，修复使用新版本。

配置和状态文件的 `schema: 1` 是持久化格式版本，不随每次发版改变。稳定插件 ID `nocoo.hermes-gateway` 和 pane ID `gateway` 保持不变，让用户配置和暂停意图延续。0.1.2 忽略旧监控偏好中的 `auto_open`，始终打开 Dashboard；其余布局、主题和采样偏好保留。Hermes 自身插件选择由 Hermes 管理，本插件不再限制其插件配置或强制关闭项目插件。

## 升级与回滚

升级会替换 Herdr 管理的源码 checkout，不属于热更新。先保存当前 tag/commit、插件配置和私有控制状态，并记下原本是否暂停。

确认已获停服授权后，在绑定的 Herdr session 内按以下顺序升级：

1. 用旧安装的 `status --json` 记录专用 pane、supervisor、Gateway 及其启动身份，执行 `stop --wait 30`。只有 `completed=true` 且状态为 PAUSED 才算 Gateway 及受管后代停止；`ORPHAN`、`UNKNOWN` 或超时需要先诊断。
2. 执行 `herdr plugin disable nocoo.hermes-gateway`，阻止生命周期 hook 重建面板。**从 0.1.2 起 Stop 会保留 supervisor 与 Dashboard**：若旧 supervisor 仍存活，先将其身份与原生 pane 的 shell PID、插件归属核对，再用 `herdr pane close <已核验的专用-pane-id>` 关闭该 pane。不要关闭用户工作 pane 或整个 workspace。旧版 supervisor 已自行退出时无需重复关闭。
3. 核验旧 supervisor、Gateway、受管后代和嵌入监控均已退出；独立只读面板另行关闭。按目标 tag 重新执行原生 `plugin install`。安装器会重新启用插件，Stop 保存的 paused 意图仍阻止 Gateway 自动启动。
4. 检查实际 `plugin_root`、`--version` 和 doctor；若路径改变，同时更新私有配置与 shell 入口链接。运行 `monitor` 恢复 Dashboard，原本运行的实例再显式 Resume，原本暂停的实例保留暂停。

上述 Stop → 禁用并关闭旧插件 pane → 安装 → Monitor / Resume 会创建使用新版代码的 supervisor，无需重启整个 Herdr session。单独执行 `restart` 只重启 Gateway 子进程，不能让已有 supervisor 加载新版代码；只关闭再打开 TUI 也不等于重启 Herdr server。

回滚采用同样顺序，安装先前的 tag。只在持久化 schema 兼容时直接回退；有 schema 迁移的版本必须写清备份和恢复方法。备份保留在本机私有目录，不提交到仓库。

## 发版步骤与当前验证

1. 确保运行时版本与 manifest 一致；把 [CHANGELOG](../CHANGELOG.md)、安装、Profile 关联设计、双语入口及验证记录作为完整文档集原子提交。
2. [CI](../.github/workflows/tests.yml) 在 Ubuntu 24.04、macOS 和 Python 3.11 / 3.14 的四个组合运行离线测试。对应 commit 的四项都通过后才能发版，tag 名也须匹配版本。
3. CI run 的 `headSha` 必须等于准备发布的 commit，四个 matrix job 的 conclusion 均须为 success；不能引用旧提交的绿灯。Linux CI 使用假 Herdr/Gateway 与真实 Linux PTY，不能替代 Herdr 冷启动、退出清理和消息验证。
4. 本仓库目前没有项目级 LICENSE，不自动授予其他项目复制、修改或再分发权利。vendored hqtui 的 MIT 声明必须保留；它只覆盖该第三方代码。许可证选择留待作者另行决定，不把缺省状态描述为 MIT 项目。
5. 在发布授权范围内，对已通过检查的**确切 commit**创建 annotated tag `v0.1.2`，推送 tag，等待相同 SHA 的 tag CI 四项通过。[Release workflow](../.github/workflows/release.yml)会再次核验 annotated tag、SHA 和四项结果，再自动创建 GitHub Release 并上传已校验的源码归档及摘要。列出安装命令、兼容版本和已知限制；0.1.2 是早期版本，未验证项必须明确列出。
6. 重新下载附件，核验 SHA-256、归档路径、launcher 可执行位、兼容 symlink、manifest/运行时版本及 vendor 声明。用官方安装器安装 tag，核对 GitHub 来源和解析后的 commit，再按[接入记录](13-cherry接入与验证.md)记录真实运行验收。

本机 Python 3.11 / 3.14 完整离线回归均为 **206 项通过**；[两次完整输出](evidence/release-0.1.2-unittest.txt)记录版本号更新前的代码回归，发布提交另由四组 CI 核验。本版覆盖常驻 Dashboard、启动受阻重试、renderer 恢复、迟到检查与 Pause 竞态、独立恢复界面和已退出 controller 的创建票据修复。[原生隔离验证](evidence/recovery-native.txt)检查 Herdr 0.9.0 的 fallback、popup 与标签冷恢复；[恢复验证记录](evidence/recovery-validation.txt)说明本机安装观察和此前未定位根因的偶发 FIFO CLI 超时。[质量评估](17-插件质量评估.md)的覆盖率属于 0.1.1 基线，未在本版重新测量。完整真实宿主生命周期、首次关联向导、Linux 真实接入和新消息/模型往返，仍需单独验证。

`v0.1.0` 的发布、167 项测试、400 次 macOS 退出竞态检查，以及官方安装后的 cherry/Discord/终端及网页监控验收，保留为[历史记录](13-cherry接入与验证.md#137-正式-010-发布安装与运行验收)。本版的确切 tag、commit、CI 和附件摘要以 [0.1.2 Release](https://github.com/nocoo/hermes-on-herdr/releases/tag/v0.1.2) 为准，历史运行快照不能代替本次升级后的现场检查。
